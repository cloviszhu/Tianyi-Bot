# 天意Bot：失败项目进度归档与工作流复盘原料

归档日期：2026-09-15。归档性质：用户终止开发，保留失败现场供工作流研究。

**结论：未交付可稳定使用的机器人；用户拒绝继续测试。不是完成、不是验收通过、不是待用户配合即可完成。** 本文记录事实与复盘假设，不授权继续开发、启动机器人或发送消息。

## 1. 冻结基线与目标

- 最后功能提交：`112858e8f8d26edb5840b9580d46c30777465860`。
- 仓库：`https://github.com/cloviszhu/Tianyi-Bot.git`。
- 最终目标：分身内微信小号自动监听指定群；同一发送者发加图指令及原图后入库；成员发关键词后回图；主 Windows 主号正常使用，不受机器人输入干扰。
- 最终部署方向：Windows 本地子会话，不是虚拟机；GUI、微信和自动化在分身内运行，主机控制器维持连接。允许分身内点击/键盘/剪贴板，不允许影响主机。
- 本轮归档只写文档、保存证据和源代码快照。不停止或注销 Windows 会话，不删除图库、软件或快捷方式，不更改系统安全设置，不修改全局 skill。

## 4. 过程摘要（不是精确工时统计）

1. 从免费微信后端出发，讨论虚拟机隔离；随后按用户选择转为不用虚拟机。
2. 主桌面多窗口绑定、UIA定位、严格后台输入约束持续受阻。绑定成功曾被作为进展，但没有打通核心闭环。
3. 转向 Windows 子会话，逐步处理创建、COM初始化、凭据提示、恢复记录、权限、卡死和快捷方式问题。
4. 先交付只读观察、离线演示、OCR及手动处理，用户反复指出要的是自动加图/取图。
5. 后期才补齐集中试运行包、后台版本选择与管理通道，开始减少对用户重开的依赖。
6. 最后两次兼容修复解决新顶层窗口类型和群信息完整 AutomationId 不匹配，真实无发送监听启动过。
7. 随后的用户测试又因连接记录复核失败中止。用户终止项目。

对话中存在大量截图、重开和“继续”请求，但本归档未做完整会话导出与计数，因此不编造总次数、工时、费用或 token 消耗。

## 5. 工作流失效分析

以下是代理对可见记录的复盘，不是用户已认可的因果结论，也不是全局 skill 本身缺陷的证明。

| 观察到的问题 | 对交付的影响 | 可提炼的工作流改进 |
| --- | --- | --- |
| 关键客户端兼容性很晚才真实验证 | 大量外围代码建立在尚未证明的输入/消息接口上 | 最先验证最高风险的最小纵向闭环；失败后再决定是否扩建 |
| 用控件计数、绑定、离线演示等阶段结果反复汇报进度 | 用户投入很多，却不能使用核心功能 | 将进度绑定到用户可执行结果，明确阻塞的关键路径 |
| 多次要求用户截图、重开、发消息 | 用户成为人工测试执行器，消耗信任 | 除登录和明确外部授权外，集中验证由代理承担；用户测试要有明确目的与停止条件 |
| 诊断过度抹去异常 | 相似失败只能反复猜测、加诊断再试 | 从第一版记录有限原因码、版本、阶段、事件顺序；保留可定位性而不记录聊天或凭据 |
| 安全检查缺少配套恢复路径 | 临时查询失败、旧文件存在变成长期无法启动 | 设计“拒绝危险操作”和“可恢复状态”两件事；安全与可用性一起验收 |
| 状态门槛多，真实闭环证据少 | 流程完备感掩盖核心不可用 | 减少低价值门禁，把证据预算放在兼容性、真实闭环与故障恢复 |
| 控制器、GUI、worker版本和快捷方式分裂 | “已更新”不等于用户运行的是新代码 | 一个发行清单显示各组件摘要与实际运行版本；统一入口和回滚 |
| 同一版本号下有多个不同 wheel 摘要 | 可追溯但不易让用户理解，容易误测 | 每个交付构建使用唯一版本/构建号，禁止以GUI标题代表完整部署版本 |
| README堆叠大量历史说明且互相冲突 | VM、主机、分身的操作说明混杂 | 当前使用说明只保留一个事实版本，历史迁入归档 |
| 重复“已修好”“可以测试”的判断尺度偏低 | 用户期待与实际状态不断错位 | 短暂ready只报告短暂ready；持续运行、重启和完整闭环分别验收 |
| 用户降低流程强度后仍长期细碎交付 | 未真正落实“先做完整再集中测”的意图 | 明确授权边界后批量实现与验证，不把每个内部失败升级成用户操作 |

不能归因于用户没有配合：用户已多次授权、操作、截图并明确需求。也不能用“个人项目简单/复杂”代替技术判断；UI自动化与会话状态的风险应早识别、早验证。

## 6. 下一版工作流的候选规则（未实施）

- 开工先定义一个可见结果：一条加图指令、同发送者一张图、一次关键词回图，且不影响主机。将它作为首要验证对象。
- 为高风险依赖预先约定探索预算、失败阈值与最小替代方案；本案未可靠统计投入，阈值由后续工作流设计确定，不追溯伪造。
- 每次要求用户操作前记录：为什么不能自动完成、这次能排除什么、失败后代理怎么继续。无明确收益就不请求。
- 发布前检查实际入口、组件版本、默认状态与文档一致；维护一个“代码/部署/真实验证”三栏清单。
- 每个阻断都区分瞬时故障、需要人工决定和不可恢复故障；保留恢复路径，不直接删安全边界。
- 每次对外报告只陈述本轮证据，明确未测项；模拟通过不能升级为真实环境通过。
- 以用户测试次数、同类故障复发次数、到首个真实闭环的时间、失败原因可定位率衡量流程，而不是以文档量或测试总数衡量。
- 流程状态应支持“取消/失败归档”，与“完成验收”分离；不能为了归档强行补成功门禁。
